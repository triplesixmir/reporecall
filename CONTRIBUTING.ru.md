# Участие в RepoRecall

Спасибо за помощь RepoRecall. Изменения должны сохранять локальный и file-first характер проекта, учитывать приватность и не требовать hosted-сервиса.

## Перед началом

- Node.js `>=22.12`.
- pnpm `11.19.0` (версия закреплена через `packageManager`).
- Временный тестовый brain, а не настоящий личный brain или реальный `CODEX_HOME`.

Не добавляйте в изменения приватные memories, credentials, абсолютные пути конкретной машины, сгенерированную SQLite-базу или артефакты `.playwright-cli`.

## Локальная разработка

```text
pnpm install --frozen-lockfile
pnpm check
pnpm test:e2e
```

`pnpm check` запускает lint, строгую проверку типов, unit/integration-тесты и сборку всех workspace-пакетов. Browser suite собирает web-приложение и запускает его через локальный preview-сервер.

## Архитектурные правила

- Markdown-файлы с YAML frontmatter — единственный durable source of truth.
- SQLite — disposable index/cache. Функциональность должна оставаться корректной после удаления и rebuild базы.
- Публичный контракт должен находиться в минимально подходящем пакете. Не импортируйте CLI или web-код в core-пакеты.
- Сохраняйте atomic writes и понятную диагностику malformed memory-файлов.
- Session captures должны быть redacted и временными. Raw transcript не сохраняется.
- Не изменяйте пользовательские tags и текст незаметно; AI-предложения должны быть различимы.
- Новые integrations по возможности должны fail open и не создавать durable memories молча.

## Как вносить изменение

1. Изучите соответствующий пакет и его тесты до изменения интерфейса.
2. Добавьте сфокусированный падающий тест для нового или сломанного поведения.
3. Реализуйте минимальное изменение, делающее тест зелёным.
4. Запустите сфокусированный тест, затем `pnpm check` и `pnpm test:e2e`, если изменение затрагивает CLI, API или UI.
5. Обновите документацию на английском и русском для пользовательского поведения.
6. Проверьте `git diff --check` и убедитесь, что в diff нет secrets или локальных путей.

Для нового вертикального среза сохраняйте явную границу пакета, при необходимости добавляйте handoff в описании коммита и документируйте ограничения вместо скрытых fallback-ов.

## Коммиты и pull request

Используйте conventional commit subject, например:

```text
feat(index): support project-aware ranking
```

Pull request должен содержать:

- краткое описание пользовательского результата;
- команды проверки и их результат;
- заметки о migration, privacy или совместимости, если они нужны;
- скриншоты или короткую запись для заметных UI-изменений;
- подтверждение, что изменение не требует hosted-сервиса.

Не смешивайте несвязанный рефакторинг с feature-изменением. Поддерживающие проекта могут попросить уменьшить patch, если поведение и cleanup трудно проверять вместе.

## Сообщение о security-проблеме

Не создавайте публичный issue для vulnerability. Следуйте [SECURITY.ru.md](SECURITY.ru.md) и удаляйте credentials из локального воспроизведения до отправки.
